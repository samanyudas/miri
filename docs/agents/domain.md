# Domain documentation

Read the root `GLOSSARY.md` before introducing domain terms.
Read relevant decisions in `docs/adr/` before changing a component's responsibilities or integration boundaries.
Miri has one domain context and one glossary.

Use the glossary's names consistently in code, issues, and explanations.
If a proposed change conflicts with an ADR, identify the conflict explicitly.
Record new accepted architecture decisions in `docs/adr/`.
Product direction stays in `decisions/`, and tasks and specs stay in GitHub Issues.
